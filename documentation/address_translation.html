📚 Page Table Capacity

Four-level x86-64 paging exposes 512 entries per level (9 bits each). With 4 KB pages, a process can theoretically map 236 pages (256 TiB) inside the 48-bit canonical window; with 2 MB pages the PD-level leaf entries top out at 227 (still 256 TiB of coverage). OS policy and available RAM still bound what gets populated. If 5-level paging is enabled, the architectural span grows to 57 bits (128 PiB), but Victima currently models the common 4-level configuration.

🧭 Leaf PT pointer caching

Victima’s walker models the four-level chain (PML4→PDP→PD→PT). Each step uses the current level’s PTE plus the next 9-bit VPN slice to form the address of the following table; the PT entry then holds the data-page PPN. To reduce repeated work, the simulator keys a cached leaf-page-table base on VPN[ PML4 + PDP + PD ]—kept alongside the STLB. On an STLB hit, that cached base is combined with the final 9 VPN bits to index the PT and fetch the PTE directly; on a miss, the same VPN trio is reused to rediscover the PT pointer before issuing the PT memory access.

x86-64 uses four 9-bit indices (PML4 → PDP → PD → PT) to cover the 48-bit canonical user space; each intermediate entry points to the next page table page, and the leaf entry supplies the physical page number. With 512 entries per level, a single process can in theory map 5124 4 KB pages (256 TiB of virtual space), though actual mappings are limited by physical memory and OS policy.

Victima caches partial walks in the shared TLB (STLB). On an STLB hit, the concatenated VPN bits for PML4/PDP/PD directly identify the cached leaf table pointer. On an STLB miss, the walker reconstructs the same three-level VPN tuple, follows the PTE pointers in memory, and then combines the final 9-bit PT index with the retrieved base to fetch the leaf PTE before completing the translation.

In the baseline flow, Core::initiateMemoryAccess forwards requests to MemoryManager::coreInitiateMemoryAccess, which immediately calls performAddressTranslation unless oracle translation is enabled. The manager dispatches demand-loads and instruction fetches to the per-core TLB via accessTLBSubsystem; TLB::lookup records an L1 TLB hit/miss and optionally an L2 cache-backed translation hit.

On a TLB miss (or L2-cache-backed miss), the manager invokes ptw->init_walk. The walker issues a four-level radix walk, relying on the cache hierarchy for PTE accesses, and returns an accumulated translation latency. That latency—whether from pure TLB access or a full walk—is added to the subsequent cache-controller access when the request continues down the hierarchy.

This bucket measures how effective early fetch is at hiding page-table-walk latency. We define three timestamps per walk:

  • t_issue: time when the early fetch is launched (at the PD service).
  • t_done: completion time for the modeled walk (the point where it would have blocked).
  • t_need: dependency time (when the leaf result is required).

Using those timestamps, compute:

  • L_pte = t_done - t_issue
  • L_tail = max(0, t_done - t_need)
  • L_overlap = L_pte - L_tail
  • overlap_ratio = L_overlap / L_pte

Report the following aggregate views:

  • Average overlap ratio.
  • Histogram/CDF of overlap ratio.
  • Histogram of tail latency (L_tail), which directly shows “how often we still waited”.
  • Early-fetch success rate: P(t_done <= t_need), or the percent of times the early fetch was ready by the need time.

Implementation note (how to collect overlap stats):

  • Record t_issue and t_done when A fires.
  • Record t_need right before B.
  • Compute L_overlap and L_tail per walk.
  • Accumulate histograms across walks.
